# Runbook 编写指南

Runbook 把一次确诊经验变成下次可快速进入的排查入口。它应保留可迁移机制，而不是复制完整事故报告。

## 何时值得沉淀

满足任一条件：

- 同类症状可能再次发生。
- 排查依赖不直观的日志、字段可信度或跨层顺序。
- 这次发现了可复用的证伪方法。
- 常见症状容易被误诊为另一个模块。

一次性配置错误、只对某个临时版本成立且不会再现的问题，可以只保留报告。

## 五段式结构

```markdown
# <症状或问题域>

## 1. 适用症状
- 用户可观察现象
- 适用环境或前提
- 明确不适用的相似症状

## 2. 最短排查路径
1. 先取哪个关联 ID 和时间窗
2. 查哪些来源与稳定事件
3. 如何判断断点位于哪一层
4. 哪些条件下应回到通用排障流程

## 3. 关键判据
| 观测 | 说明 | 不能证明什么 |
| --- | --- | --- |
| … | … | … |

## 4. 常见误判
- 容易被当成什么
- 哪条反证可以排除
- 哪些字段或日志不可靠

## 5. 确认后的动作
- 修复方向
- 回归与运行时验证
- 需要保留或补充的长期观测
```

## 提炼原则

- 只写调查材料能够支持的事实；缺失信息标为 `TODO` 或 `unknown`，不为填满模板而推测。
- 从“某次发生了什么”提炼成“以后看到什么，先查什么”。
- 保留事件模式和判断条件，删除用户、机器、绝对路径和一次性 ID。
- 真实值换成语义占位符。
- 不把单次根因写成唯一可能；写清退出条件。
- Runbook 是启发式加速器，不是必须逐条执行的脚本。
- 新经验与旧 Runbook 冲突时，先核实适用边界，再更新文档。
- 按目标仓库已有机制把 Runbook 登记到症状入口、目录或索引；仓库没有索引时不额外建设系统，只保证相邻文档能够发现它。
- 完成后检查新增链接、锚点和导航入口可达。
