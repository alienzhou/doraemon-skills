# 产品文档七段结构模板

落点：`<产品文档目录>/<NN>-<feature-slug>-prd.md`
截图：`<产品文档目录>/images/<feature-slug>/`

若你的项目另有文档命名与文档头规范，以项目规范为准。

## 写作总原则

**简略，不给读者阅读压力。** 截图承担大部分解释职责，文字只补图说不清的部分。读者是产品/研发同事，不是没上下文的外人——不要铺垫，直接进入痛点。

## 各段落的常见失手

| 段落 | 容易写坏的地方 |
| --- | --- |
| 一 | 从竞品讲起而不是从用户痛点讲起，读者会觉得「为了抄而抄」 |
| 一 | 不写自己这边的现状原文（组件/文案），差距说不清 |
| 三 | 只放全屏截图，细节看不清；要用 `sips` 裁剪 |
| 三 | 只描述「有什么」，不说「为什么这么设计」；「巧妙之处」小表是这篇文档的价值密度所在 |
| 四 | 只写入口不写生命周期，评审时必被问「换个会话还在吗」 |
| 六 | 不写边界，需求会被无限放大 |
| 七 | 验收写成主观描述，要写成可勾选的行为 |

## 命名一致性

涉及核心对象、模块名、协议字段、状态、事件命名时，先确认项目是否有既定的领域语言清单（如 `domain-language.md` 之类），按清单用词，不要自造同义词。没有清单时，至少保证同一篇文档内用词自洽。
