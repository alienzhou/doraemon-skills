# 需求任务字段与描述模板

> 本文是**平台无关**的模板。字段 key、选项 ID、项目/分组标识都取决于你的需求管理系统，
> 凡 `<...>` 处替换成你环境里的实际值。**不要硬编码任何来自别处的 ID。**

## 一、先固定一组坐标

开工前把这几个值查出来写在一处，之后每次建任务直接复用：

| 维度 | 你的值 | 怎么拿 |
| --- | --- | --- |
| 项目 ID | `<P...>` | 平台项目设置页 / `project list` 类命令 |
| 分组（需求池）ID | `<S...>` | 你要往哪个池子里投需求 |
| 任务分类 ID | `<...>` | 「产品需求」而非「技术需求」 |
| **参照任务** | `<T...>` | **同分组里一条字段填得最全的任务** |

**参照任务是这张表里最重要的一行。** 与其逐个字段查文档，不如直接读一条已有任务的完整 JSON，比照着填——字段名、取值格式、必填项一次看全。

> 本 skill 建的是**产品需求**（只到需求 idea 阶段，不碰发布流程）。如果你的流程里还有「技术需求 + 变更单」那一层，那是另一个环节的事，不在本 skill 范围。

## 二、字段填写建议

| 字段 | 竞品调研场景的取值 |
| --- | --- |
| 标签 | **打两个**：一个标来源池（如「自动需求采集」），一个标性质（如「竞品调研」） |
| 来源类型 | 「竞品」 |
| 来源备注 | 自由文本：`<竞品> <日期> Changelog + Computer Use 本机实机调研` |
| 反馈类型 | 「产品功能优化」 |
| 状态 | 默认落在「需求 idea」类的初始态，**不要主动流转** |
| 产品模块 / 功能模块 | 按功能实际归属选 |
| 优先级 | 默认「中」，除非有明确理由 |
| 执行人 / 报告人 | 你自己的账号（多数平台创建时必填） |

### 标签的两个坑

**坑一：要打两个标签。** 只打来源池标签，竞品来源的需求会和群反馈、文档采集的需求混在一起，事后筛不出来。加一个性质标签才能单独看这批。

**坑二：标签 ID 必须来自项目标签池。** 全局字段接口返回的是全公司/全组织标签池，那里的 ID 传进去平台会接受，但**回读渲染成裸数字**（因为该 ID 不属于本项目）。

正确做法：

```bash
# 1. 查项目级标签列表，拿到项目内可用的那个 ID
<平台 CLI> label list <项目ID> --size 200 | grep -i "<关键词>"

# 2. 项目池里没有就先建
<平台 CLI> label create "<名称>" --project <项目ID> --color '#1E6FFF'

# 3. 改完回读，看到的必须是中文名而不是数字
<平台 CLI> task view <taskId> | grep -i label
```

注意有些平台的标签有两个 ID（记录 id 与字段项 fieldItemId），**写入时要用字段项那个**。

## 三、描述 HTML 模板

存到 `/tmp/task-desc.html` 后用 `cat` 注入（不要在 shell heredoc 里直接内联中文 HTML，容易踩编码问题）。

```html
<h2>一、需求介绍</h2>
<p>当前<strong>&lt;现状痛点一句话&gt;</strong>。</p>
<p>但真实场景里：</p>
<ul><li>&lt;场景 1&gt;</li><li>&lt;场景 2&gt;</li></ul>
<p>结果是：<strong>&lt;后果&gt;</strong>。</p>
<p>本需求<strong>&lt;要做什么&gt;</strong>。<strong>不新增页面、不动协议主干</strong>，本质是&lt;一句话本质&gt;。</p>

<h2>二、竞品来源（可复核）</h2>
<table>
<tr><td><strong>竞品</strong></td><td>&lt;产品名&gt;</td></tr>
<tr><td><strong>发布版本</strong></td><td>&lt;版本号&gt;</td></tr>
<tr><td><strong>发布日期</strong></td><td>&lt;YYYY-MM-DD&gt;</td></tr>
<tr><td><strong>官方发布说明</strong></td><td><a href="&lt;带锚点的 changelog URL&gt;">&lt;标题&gt;</a></td></tr>
<tr><td><strong>官方原文</strong></td><td><code>&lt;一字未改的原文&gt;</code></td></tr>
<tr><td><strong>取证方式</strong></td><td>&lt;本机实机截图 / 官方快照测试 / 官方产品物料&gt;</td></tr>
</table>
<p><strong>取证方式说明</strong>：&lt;有无实机、为什么、限制在哪&gt;</p>

<h2>三、一期范围边界</h2>
<ul><li>不做 &lt;A&gt;</li><li>不做 &lt;B&gt;</li></ul>

<h2>四、详细产品文档</h2>
<p>含<strong>竞品实机演示截图</strong>、<strong>我们的交互方案</strong>、<strong>背景与用意</strong>：</p>
<p><a href="&lt;文档 URL&gt;">&lt;文档标题&gt;</a></p>
```

要点：

- `<a href>` 必须带**文字标题**，不要放裸 URL（裸 URL 在多数平台里不可点）。
- 快捷键、命令、Skill 名用 `<code>` 包。
- 任务正文只到「四段」为止，任何更细的方案都放文档。
- 需要图时用 `<img src>`，地址先走平台的附件上传拿 CDN。默认不加图，保持任务单精简。

## 四、「竞品来源」块的硬要求

一句「某竞品于某日 Changelog 上线了某功能」**不算来源**。读者的第一反应必然是「哪个版本？哪条更新？我上哪看原文？」。来源块必须让人**不问一句就能自己复核**，因此固定用 `<table>` 承载六个字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 竞品 | ✅ | 精确到产品线（如「OpenAI Codex CLI」而非「OpenAI」） |
| 发布版本 | ✅ | 版本号原文（`rust-v0.152.0` / `ChatGPT for iOS 1.2026.237`）。无版本号的写发布批次名 |
| 发布日期 | ✅ | `YYYY-MM-DD` |
| 官方发布说明 | ✅ | **带锚点**的可点链接。链接前必须 `curl -sI` 验过状态码 |
| 官方原文 | ✅ | `<code>` 包，**一字不改**（含英文原文，不要只给翻译） |
| 取证方式 | ✅ | 实机截图 / 快照测试 / 官方物料，并说清限制 |

四条配套规则：

1. **多版本演进的功能，给逐版本锚点表。** 一个功能分三次做完时，「先建能力 → 入口下沉 → 升级自检」这条演进路径本身往往比终态更值钱——它告诉你哪一步是弯路。每行一个可点锚点，读者能逐条核。
2. **开源取证的，给可复核引用文件清单。** 列出 `<path>` 与 `ref=<tag>`，读者能自己 `gh api` 拉一遍。
3. **没有官方 changelog 条目的，必须如实说明。** 实机操作时偶然发现的功能，要明写「**本条不是从 changelog 采集来的**，官方 changelog 中相关条目共 N 条，无一提到本功能，唯一一手证据是实机截图」。**不要为了让来源块看起来完整而硬塞一个不相关的 changelog 链接。**
4. **链接失效要换，不要留着。** 官方帮助中心的 release notes 页经常改版甚至返回 403，换源时在正文补一句说明，别让读者以为原文变了。
