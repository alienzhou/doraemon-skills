# 竞品需求采集闭环

把竞品的**一个小粒度功能**，变成需求池里一条**有实机证据、有交互方案、字段齐全**的需求任务。

这个 skill 的价值不在「抓 changelog」（那是基本盘），而在补上三件别人不会主动做的事：**粒度控制**（不挑大模块）、**实机取证**（不靠文档推断）、**双层交付**（任务单精简、方案沉文档）。

> **平台无关**：本 skill 只约束方法论。文档落到哪个知识库、任务建到哪个需求管理系统（Jira / Linear / 飞书 / 内部平台……），由你的环境决定——凡出现 `<文档平台>` / `<需求平台>` 的地方，替换成你实际使用的工具即可。步骤 5、6 给的是**校验要求**，不是某个具体 CLI 的用法。

---

## 核心闭环（六步）

```
① 采集     抓竞品 changelog / 发布说明 → 落盘留档
      ↓
② 选题     用粒度判据筛出 1~2 个小功能（大模块拆细，拆不动就换）
      ↓
③ 取证     Computer Use 操作真机竞品客户端 → 截图 + 辅助功能树双证据 → 还原现场
      ↓
④ 文档     七段结构，截图内联
      ↓
⑤ 上传     Markdown + 图片打包上传到<文档平台>，回读校验图片齐全
      ↓
⑥ 建任务   固定字段模板 + 富文本描述 + 指向文档的可点击链接
```

**四者齐了才成闭环**：粒度小、证据真、文档轻、任务字段全。

### 交付门禁（缺一项不建任务）

在创建需求任务前逐项核对，任何一项缺失就停在补证据阶段，不用「待补」占位交付：

| 门禁 | 必须满足的事实 | 验证方式 |
| --- | --- | --- |
| **粒度** | 选题已过**三道闸全通过**（一句话说得清 / 一个交互点验完 / 一期能独立上线），且本轮采集不超过 2 个功能 | 已向用户报「选了什么、淘汰了什么、为什么」并得到默认或明确认可 |
| 网络调研 | 已读取竞品官方一手资料（changelog / release notes / 官方功能页），并在产品文档写明来源、日期与可访问链接 | 文档有「网络调研证据」小节 |
| 真机调研 | 已通过 Computer Use 操作真实竞品客户端，文档写明关键交互结论与辅助功能树证据 | 文档有「Computer Use 实机取证」小节 |
| 截图 | 每个关键交互步骤至少一张；截图已内联到 Markdown，并在上传后的回读中确认全部入库 | 本地图片数 = 平台回读的图片数，且跳过数为 0 |
| 文档 | 已将「网络调研 + 真机取证 + 截图 + 我们的交互方案」上传为一篇文档 | 上传返回文档 ID，且导出回读成功 |
| 任务 | 已按字段模板建任务，且富文本中有**带标题、可点击的文档链接** | 回读字段与描述；页面打开后链接可点 |

> **粒度门禁最先判、也最不能让步**：它在步骤 2 就该拦住，一旦放过去，后面的取证、文档、任务都会围着一个说不清的大模块空转。宁可空手回来说「这批 changelog 没有合适粒度的功能」，也不要交付一个大模块需求。

> **详细文档在任务中的留存方式**：文档是完整方案的事实源；任务不复制一份文档正文，而是将文档以带标题的 `<a href>` 链接永久写入任务描述的「详细产品文档」章节。这样任务是需求入口与追踪载体，文档是可阅读、含截图的完整调研档案，避免两份正文漂移。

---

## 三条硬约束（最高优先级）

1. **粒度小于一切**。一个功能如果「一句话说不清」「要验多个交互点」「一期不能独立上线」，就不是本 skill 的对象。大模块必须拆细挑一个点；拆不动就换功能。

2. **证据来自实机，不来自文档推断**。changelog 只用来锁定功能，具体交互（快捷键在哪、提示什么时候出现、状态呈现在哪）必须在真机上操作出来。截图 + 辅助功能树两路互证，缺一路就标注为「未验证」而不是猜。

3. **竞品现场必须还原**。在竞品产品里的任何状态改动（设置、开关、输入）操作完必须撤销，并用 `--expect` 验证撤销生效。不产生持久数据、不删除、不发送、不发布。

> 一句话心法：**粒度控住、证据做实、任务写薄、方案沉厚。**

## 何时使用 / 何时不用

| 用本 Skill | 不用 |
| --- | --- |
| 看到竞品某个功能不错，想变成自己的需求 | 从 0 写完整 PRD（没有竞品对象） |
| 需要实机截图佐证交互细节 | 已定版方案要建研发任务 / 发起变更流程 |
| 要往需求池里补一条有据可查的需求 | 已有 PRD 要落代码 |
| 竞品功能拆解 + 自己的交互方案设计 | 纯讨论方向、不出任务 |

## 步骤 1 · 网络调研：采集官方一手资料

抓竞品官方 changelog / release notes / 官方功能页，落到本地留档（例：`.firecrawl/<vendor>-changelog.md`）。

- 优先官方一手来源，不用二手解读文章。
- 至少保留：**来源标题、发布日期、原始 URL、与本功能直接相关的原文摘录**。
- 记下版本日期，后面产品文档的「网络调研证据」和任务的「来源备注」都必须写。
- 网络资料只用来锁定功能与补充背景；具体交互结论仍需经下一步真机验证，不能把网页描述当作实机事实。

## 步骤 2 · 选题：粒度判据（本 skill 最容易失手的一步）

**一次只采 1~2 个功能。** 贪多必然导致每个都调研得浅，还会把大模块混进来。

对候选功能逐条过三道闸，**三条全过**才进入取证：

| 判据 | 通过 | 不通过 |
| --- | --- | --- |
| 一句话能说清它解决什么问题 | ✅ | 需要铺垫背景才能讲明白 → 淘汰 |
| 一个交互点能验完 | ✅ | 要跨多个页面 / 多个状态机 → 淘汰或拆细 |
| 一期能独立上线 | ✅ | 依赖云端环境、调度系统、长期状态 → 淘汰 |

### 快速自检（任一命中即判为过大）

- 描述里出现「体系」「重构」「打通」「全链路」「平台化」这类词
- 说清楚它需要先解释两个以上的新概念
- 取证要在三个以上界面之间来回跳
- 落地必须同时改客户端 + 服务端 + 调度
- 想不出一个能一句话写完的验收标准

**大模块的正确处理**：不是放弃整个方向，而是**从中切出一个能独立成立的交互点**。切不出来就换功能，不要硬做。

**典型反例**（真实淘汰过的）：子 Agent 独立 VM、订阅体系改版、目标驱动的任务编排——都是大模块，涉及后端与长期状态机。
**典型正例**：Skill 固定为对话模式（一个快捷键 + 一枚徽标，验完就懂）。

选完**必须先向用户报一句**「选了什么、淘汰了什么、为什么」，不要闷头往下走。如果整批 changelog 都没有合适粒度的功能，**如实说没有**，这是可接受的结果。

## 步骤 3 · 实机取证（Computer Use）

依赖 Computer Use 类能力（macOS GUI 观察与操作）。**Electron 类竞品客户端（Cursor / VSCode 系）有专属坑，动手前先读 `references/capture-pitfalls.md`**，那里有 AX 树懒加载、多显示器负坐标截图、前台抢占三个必踩的坑。

取证要求：

- **每个关键步骤一张图**，典型是三张：初始态 → 触发态（菜单/提示出现）→ 结果态（状态呈现）。
- 截图后用 `sips -c <h> <w> --cropOffset <y> <x>` 裁出关键区域，全屏图看不清细节。
- **辅助功能树作为第二路证据**：把 `cu observe` 里相关节点的 role / value / description 记下来，写进文档当佐证（例如「徽标由 AXStaticText + description="Remove xxx" 的 AXButton 组成」）。
- **操作完还原现场**，用 `--expect '{"until":"absent","text":"<标识>"}'` 验证。

截图落到产品文档同级的 `images/<feature-slug>/`。

## 步骤 4 · 产品文档

写到你的产品文档目录下，文件名建议 `<NN>-<feature-slug>-prd.md`。文档头带上 `状态` / `更新时间` / `来源`（若你的项目另有文档规范，以项目规范为准）。

**固定七段结构**（模板见 `references/doc-template.md`）：

1. 这个功能解决什么问题 —— 从用户的真实困境写起，不从竞品写起
2. 网络调研证据 —— 官方来源、发布日期、原始链接与相关原文摘录
3. 竞品怎么做的（Computer Use 实机演示）—— 分步骤 + 内联截图 + 辅助功能树证据 + 「这个设计的巧妙之处」小表
4. 我们的交互方案 —— 入口 / 状态呈现 / 生效范围与生命周期 / 需要澄清的点
5. 为什么值得做
6. 范围边界（一期不做）
7. 验收要点

> 网络资料和真机结果都必须进入同一篇产品文档：前者说明「竞品公开承诺了什么」，后者说明「用户实际看到与操作到什么」。两者不相互替代。

**文档要简略，不给读者阅读压力**——截图承担大部分解释职责，文字只写图说不清的部分。

## 步骤 5 · 上传到文档平台

把 Markdown 与图片一起上传，让截图随文内联。具体命令取决于你的<文档平台>，但**三条校验要求与平台无关**：

1. **图片零丢失**：平台回读的图片数必须等于产品文档实际内联图片数，跳过数必须为 0；不满足就先修复打包路径或图片引用再继续。
2. **正文完整**：导出的 Markdown 必须同时包含「网络调研证据」与「Computer Use 实机取证」的结论；任一缺失都不得建任务。
3. **拿到可访问 URL**：记下文档的打开地址，下一步必须用它写进任务描述的可点击链接。

> 多数文档平台的 Markdown 导入接口不接受裸 `.md`（图片会丢），通常需要把 `md + images/` 打成 zip 一起传，并保持 zip 内相对引用路径不变。上传链路的具体踩坑见 `references/capture-pitfalls.md` 第三节。

## 步骤 6 · 建需求任务

字段模板与富文本写法见 `references/task-fields.md`。

**标签建议固定打两个**：一个标识**来源池**（如「自动需求采集」），一个标识**需求性质**（如「竞品调研」）——后者让竞品来源的需求能被单独筛出来看，不与其他来源的需求混在一起。

**任务描述尽量用富文本**——多数需求平台的描述字段底层存 HTML，传纯文本会渲染成一坨段落，链接也不可点。用 `<h2>` 分章、`<ul><li>` 列举、`<strong>` 强调、`<code>` 包代码与快捷键、`<a href>` 挂文档链接。

**任务正文只写四段**（保持精简，详细方案在文档）：

1. 需求介绍 —— 问题 + 要做什么，一段讲完
2. 竞品来源 —— 哪家、哪个 changelog、已实机验证
3. 一期范围边界 —— 不做什么
4. 详细产品文档 —— 文档超链接（带标题的 `<a>`，不是裸 URL）

建完执行两类回读校验：

1. **字段**：项目/分组、类型、状态、标签、来源类型、来源备注、优先级等与 `references/task-fields.md` 的模板一致。
2. **文档留存**：任务描述是富文本，且「详细产品文档」章节中存在指向文档 URL 的**带标题可点击链接**，链接标题明确说明其中包含网络调研、Computer Use 实机结果和截图。

确认通过后，把文档链接和任务链接一起报给用户。
