# 数据与可信度

没有真实参数的课件是空壳。这份文档规定数据怎么找、怎么标、怎么让读者验算。

## 为什么必须用真实参数

构造出来的「好看的数」有三个问题：

1. 读者无法验算，只能选择信或不信
2. 数字之间的比例关系往往不成立，推出的结论是假的
3. 读者学完无法迁移到自己的场景

真实参数的额外好处：**反直觉的结论往往来自真实数据的不均衡**。
比如 H100 带宽是 4090 的 3.3 倍但算力是 6 倍，导致拐点更高、浪费比例更大——
这个结论你编不出来。

## 基准对象的选择

挑一个**最容易验证**的具体对象，不要用「一般的服务器」这种虚指。

| 主题类型 | 基准对象举例 | 选择理由 |
|---|---|---|
| 硬件性能 | RTX 4090 | 官网规格公开，参数好查 |
| 网络协议 | HTTP/2 over TLS 1.3 | RFC 有明确定义 |
| 云成本 | AWS us-east-1 按量价目 | 有公开价目表 |
| 数据库 | PostgreSQL 16 默认配置 | 文档有默认值 |

选择标准：

- **可查证** —— 读者搜一下就能对上，不需要信任你
- **数字关系好讲** —— 比如 4090 的拐点刚好是 164，容易说清「batch 要开到一百多」
- **常见** —— 读者大概率接触过或听过

在侧栏或首屏固定显示基准，让读者随时知道「这些数字是哪来的」。

## 三级可信度标注

每个数字必须归入一类，并在页面上用标签显示。

| 级别 | 标签样式 | 含义 | 举例 |
|---|---|---|---|
| **官方规格** | `.src-t.spec` 绿 | 厂商/标准文档明确标注 | 1008 GB/s |
| **推导值** | `.src-t.calc` 青 | 由官方值算出，非独立数据 | 拐点 164 |
| **量级近似** | `.src-t.appr` 琥珀 | 实测有差异，取通用值，写 `~` | ~60 GB/s |

```html
<tr>
  <td>显存带宽</td>
  <td class="mono">1008 GB/s</td>
  <td><span class="src-t spec">官方规格</span></td>
  <td>384-bit × 21 Gbps ÷ 8 = 1008，可自行验算</td>
</tr>
```

**第四列写验算方式**，这是让读者建立信任的关键。不要只给结论值。

## 推导值要写出算式

```
Roofline 拐点 = 165e12 ÷ 1008e9 ≈ 164 FLOP/Byte
```

而不是只写「拐点 164」。写出算式有三个作用：

1. 读者能验算
2. 换基准对象时知道怎么重算
3. 暴露你用的是哪个版本的输入值（如 dense 还是 sparse 算力）

## 容易出错的坑

### 选对版本的数值

同一个指标常有多个口径，必须说明用了哪个：

- GPU 算力：**dense 还是 sparse**（4090 是 165 vs 330，差一倍）
- 内存带宽：**理论峰值还是实测**（DDR5-4800 双通道理论 76.8，实测约 60）
- 存储速度：**顺序还是随机**、**读还是写**
- 网络延迟：**RTT 还是单向**

页面上要写清楚。用了保守值（如 dense）要说明没用那个虚高的。

### 两套进制并存

`GB` 可能是十进制 10⁹ 也可能是二进制 2³⁰（GiB），差 7.4%。
统一一种并说明：

> 本页统一按十进制：`7e9 × 2 = 1.4e10` 字节 = 14 GB；按 GiB 算则是 13.04 GiB。
> 估算瓶颈时可忽略，但**下载模型文件对体积时会对不上**。

最后那句很重要——告诉读者这个差异在什么场景下会咬人。

### 简化模型要声明边界

如果教具用了简化公式，必须说清楚简化掉了什么、什么时候不成立：

> `2 × 参数量 = 单 token FLOP` 是业界标准估算，忽略了 attention 的 KV 计算、
> LayerNorm、softmax —— 短上下文误差在 10% 内，**长上下文时 attention 项会显著上升，
> 这页的估算不覆盖那种场景。**

区分「数学上严格的部分」和「我的简化模型」：

> 期望接受长度公式来自 Leviathan 等人 2023 年的论文，**数学上严格**。
> 而「单轮成本」是我按 Roofline 位置做的**简化模型**，
> 定性趋势可靠（带宽瓶颈时近乎免费、算力饱和时正比于 K），但**具体数值不等于实测**。

## 换基准对比

做一组可切换的基准对象，让读者看到「换一个会怎样」。
这是把单点知识变成可迁移理解的最有效手段。

```js
const GPUS=[
  {n:'RTX 4090',bw:1008,peak:165,note:'本页基准。拐点 164...'},
  {n:'H100 SXM',bw:3350,peak:990,note:'拐点最高。算力涨得比带宽快...'}
];
// 拐点由参数算出，不硬编码
const ridge=g.peak*1e12/(g.bw*1e9);
```

**所有派生值都要从参数实时计算**，不要为每个对象硬编码结论。
这样读者改一个参数就知道会怎样，也避免对象之间的结论不自洽。

挑选对比对象时，优先选能**体现反直觉关系**的（如上面 H100 的例子），
而不是单纯列举几个型号。

## 数据来源模块

单独做一个模块（通常放最后）集中交代来源，包含：

1. 基准对象的逐项参数表，带三级标签和验算方式
2. 换基准对比的交互
3. 「为什么选这个基准」的说明
4. 模型侧/算法侧公式的来源和简化边界

这个模块是课件可信度的落脚点。读者如果怀疑某个数，应该能在这里找到答案。
