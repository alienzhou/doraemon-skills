# 教具设计

教具是 L0 层，课件的主体。这份文档讲**怎么判断教具自解释了**，不规定用什么形态实现。

## 最小完整形态

```
可调参数 ──→ 实时读数（数值是多少）
         └──→ 结论（这些数值意味着什么）
```

**第三项最常被漏掉。** 只给数字不给解读，读者的典型反应是
「我看懂数字在变，但不知道这意味着什么」。

## 自解释四问

做完一个教具按这四条自查。任一条答不出就是没做完。

### 1. 不读页面任何正文，能不能操作？

把所有正文段落隐藏掉，教具还能用吗：

- 滑块知道在调什么（标签 + 单位）
- 图形颜色/状态的含义清楚（**图例要放在教具旁边，不是下方**）
- 读数知道是什么指标
- 多状态元素有状态说明

### 2. 读数变化的含义是否自明？

**每个读数要有参照值或算式。** 这一行最容易省，但很重要：

| 只有值 | 加了参照 |
|---|---|
| 算术强度 1.0 | 算术强度 1.0 ／ 拐点 = 164 |
| 单步耗时 13.9 ms | 单步耗时 13.9 ms ／ 14 GB ÷ 1008 GB/s |
| 算力利用率 0.6% | 算力利用率 0.6% ／ 闲置 99.4% |

「1.0」本身没有意义，有了「拐点 164」读者才知道这个 1.0 是大还是小。

参照可以是：临界值、算式、对比基准、换算关系。

### 3. 有没有一句话告诉我「所以呢」？

结论必须**随参数改写**，包括状态名、配色、正文。不是一段静态文字。

```
batch=1   → ■ 带宽瓶颈
            算术强度 1.0 低于拐点 164，GPU 大部分时间在等权重搬进来。
            算力只用了 0.6% —— 有 99.4% 闲置，投机解码可以几乎免费地利用这部分。

batch=512 → ■ 算力瓶颈
            算术强度 512 已越过拐点，算力被打满（100%）。
            此时任何额外计算都要付真实时间代价，投机解码的开销不再免费。
```

两个额外要求：

- **数值嵌在文字里**，不要写死
- **指向下一个模块** —— 「这正是投机解码能白捡性能的场景」，让教具之间形成因果链

### 4. 看不懂某个元素时，能不能查？

关键元素要有说明入口：参数有 `?`、术语可悬浮、多状态元素逐个可查。

## 常见形态（参考，不是清单）

按主题选，也可以发明新的。**唯一约束是过上面四问。**

| 形态 | 适合 | 注意 |
|---|---|---|
| 层级对比条 | 跨数量级的容量/速度/成本对比 | 宽度用 log 映射，否则最小的看不见 |
| 流程动画 | 有时序、需要看到「反复发生」 | **必须可暂停可变速**，配累计读数 |
| 参数滑块 + 坐标图 | 有定量关系、存在临界点 | **临界点要显式画出并标数值**，区域着色 + 区域名 |
| 档位沙盘 | 离散档位的权衡 | 同时展示权衡的两端（如占用 vs 保真） |
| 逐轮回放 | 多状态离散过程 | 见下 |
| 树 / 图 | 层级或依赖关系 | 当前路径高亮，非主路径降噪 |
| 时序泳道 | 多方交互的协议 | 标注每段耗时，总时长可对比 |

动画的判断：**能用静态图说清的不要做动画。** 动画是为了说明「量的累积」或
「时序先后」，不是为了好看。

## 多状态离散过程要展开

这是真实迭代中改动最大的一处，值得单独说。

**错误做法**：一排彩色方块。读者看不出每个方块代表什么、为什么是这个颜色。

**正确做法**：逐轮展开，每轮一行。

```
第 1 轮   const   d̶a̶t̶a̶   ⌐async⌐  →  result
得 2 个    猜对     猜错    没验到     补正
```

要点：

1. **每种状态有独立视觉编码**，并在顶部给图例
2. **每个元素可查**，悬浮说明它的具体遭遇
   （「第 2 个草稿猜的是 data，但主模型答案是 result → 不一致，丢弃并截断」）
3. **行首有本轮汇总**（「第 1 轮 得 2 个」）
4. **下方一句旁白**，自动改写，直接回答「所以呢」
5. **示例数据必须能体现差异** —— 如果「错误值」和「正确值」用同一份数据，
   对比就不成立。要准备两套（正确序列 + 似是而非的错误序列）
6. **随机序列要固定** —— 用预置数组而不是实时随机，
   否则拖滑块时整片乱跳，读者无法建立因果感

第 5 条是真实 bug：原版的「猜错 token」和「补正 token」取自同一词表，
显示出来是同一个单词，「纠正」这件事根本看不出来。

## 预设按钮

滑块之外提供几个有名字的预设，降低探索成本：

```
[本地单用户]  [小型服务]  [云端 API]
```

**用场景名而不是参数值。** 读者往往不知道「batch=256」对应什么情况，
但知道「云端 API」是什么。手动拖滑块时要清除预设选中态。

## 教具之间的因果链

单个教具解释一个点，整页要形成链条。在模块导语和结论里显式串起来：

```
权重太大，只能住 VRAM
  ↓
每生成 1 个 token 要把全部权重搬一遍
  ↓
搬 14 GB 却只算 14 GFLOP → 算术强度 ≈ 1，远低于拐点 164
  ↓
带宽瓶颈：算力利用率 0.6%
  ↓
三条出路 → 量化 · batching · 投机解码
  ↓
但 batching 会推高算术强度，越过拐点后投机解码的「免费」前提消失
```

最后做一个「全景速查」模块把链条压缩成一页，便于回看。
这个模块可以没有交互，纯粹是回顾。

## 读数卡的组织

数量控制在 4-6 个。超过就该拆成两组，或者检查是否有冗余。

每张三行：指标名（小）、数值（大，等宽）、参照（小）。
**所有数值用等宽字体**，否则拖滑块时数字宽度跳变，视觉抖动。
