# Ops Logging

让新代码从写下来的那一刻起，就具备被日志和代码共同解释的能力。

## 职责边界

本 Skill 负责开发阶段的长期观测建设：日志随功能代码交付，默认作为生产资产保留。它不调查具体事故，也不为某个未决假设设计临时实验。

三个 Skill 可以独立使用，也可自然衔接：

```text
ops-logging 生产长期证据
      ↓
ops-troubleshooting 消费已有证据
      ↓ 证据不足
ops-diagnostic 针对假设补造证据
      ↓
有长期价值的埋点回流日志规范
```

## 工作流程

### 1. 读取当前仓库约定

先搜索并阅读项目已有的 logging、observability、telemetry、tracing 文档和相邻代码。确认：

- 使用哪个 logger，禁止绕过现有抽象另起一套。
- 事件名、级别、字段和错误序列化约定。
- correlation ID 由谁注入，避免重复或错误传递。
- 敏感字段、采样、容量和性能限制。
- 运行时实际使用的依赖版本。

若仓库没有明确规范，读取 [references/logging-principles.md](./references/logging-principles.md)，采用其中的最小基线，不额外建设日志框架。完整合成示例见 [references/example.md](./references/example.md)。

### 2. 画出本次改动的数据流

只覆盖本次改动影响的链路。标出：

- 输入从哪里进入。
- 经过哪些关键边界、状态和外部依赖。
- 成功结果从哪里离开。
- 哪些分支可能静默跳过、拒绝、去重或不产生写入。

### 3. 找观测断点

逐个检查以下位置是否能回答“断在哪里、为什么”：

- 受理与拒绝。
- 跨模块、进程、队列、网络或存储边界。
- 关键状态迁移和终态。
- 重试、降级、超时、取消与幂等去重。
- `skipped`、`blocked`、`no_change`、`no_write` 等静默路径。
- 外部依赖调用的阶段结果与耗时。

不要给每个函数都加日志；只补能缩小故障范围的证据。

### 4. 设计稳定事件与判别字段

每条日志先回答两个问题：

1. 未来它能区分哪些故障情况？
2. 仅凭这条日志的字段，能否判断走了哪个分支或发生了什么变化？

优先使用：

- 存在性：目标是否存在。
- 状态差异：`previous` 与 `next`。
- 数量差异：处理前、过滤后、写入后。
- 分支原因：为什么跳过、拒绝或降级。
- 时间差：阶段耗时、排队时间、外部调用时间。
- 结果分类：成功、可重试失败、永久失败、取消。

事件名保持稳定、低基数；变量放结构化字段，不拼进 message。完整检查表见 [references/logging-principles.md](./references/logging-principles.md)。

### 5. 实现并验证

- 只修改本次数据流涉及的代码和相邻测试。
- 长期日志与对应功能在同一变更中评审和交付，不把观测留给后续补丁。
- 从首次提交起使用正式、稳定的事件名；`debug`、`temporary`、`test` 等一次性命名属于 `ops-diagnostic`，不应成为长期事件。
- 不记录凭据、会话内容、完整请求体或其他敏感数据。
- 运行项目要求的 lint、typecheck 和测试。
- 优先走一次最小路径，确认日志确实产生、字段可解析、关联 ID 可串联。
- 若当前环境无法运行该路径，改用 logger 测试、契约测试或静态校验，并在输出中明确标记尚未完成的运行时验证及其原因，不伪称已验证。
- 若新增稳定事件，按仓库约定更新日志规范或事件词典。

## 完成判据

交付前确认：

- 新增或变化的数据流没有关键观测断点。
- 日志能解释成功、失败和重要静默分支。
- 字段具有判别力，而不只是“执行到这里”。
- 日志不改变控制流，不泄露敏感数据，不制造明显噪声。
- 实际运行已验证事件会产生；若环境不允许，已明确记录替代验证和未验证项。
- 相关测试和仓库内日志文档已按需同步。

## 输出

简要说明：

1. 覆盖了哪条数据流。
2. 新增或调整了哪些事件及判别字段。
3. 哪些路径已有日志所以没有重复添加。
4. 做了哪些验证。
5. 仍存在什么观测盲区。
