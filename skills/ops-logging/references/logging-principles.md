# 面向排障的日志原则

在项目缺少明确日志规范时使用本基线；若项目已有约定，以项目约定为准。

## 1. 先确定日志要回答的问题

高价值日志通常能回答至少一个问题：

- 请求或任务是否进入这一层？
- 它为什么被接受、拒绝、跳过或降级？
- 哪个状态发生了变化？
- 数据在哪个边界停止继续传播？
- 终态由谁、因为什么产生？
- 哪一阶段消耗了异常时间？

只说明“代码执行到了这里”的日志通常价值较低。

## 2. 最小结构

按项目命名约定映射以下概念，不要求强行使用同名字段：

| 概念 | 作用 |
| --- | --- |
| timestamp | 排序与计算阶段耗时 |
| level | 区分调试、正常状态、风险和失败 |
| event/message | 稳定、低基数的事件名 |
| service/module/component | 定位责任边界 |
| correlation ID | 串起跨层时间线 |
| outcome/reason | 说明结果和分支原因 |
| duration | 定位慢阶段 |
| context | 放置有界、结构化的判别字段 |

变量不要拼进事件名，否则难以聚合和精确查询。

## 3. 关键打点位置

### 入口与出口

记录受理结果，而不是完整输入：

- 输入类型和有界摘要。
- 关联 ID 是否存在。
- 验证结果。
- 输出类型、数量和结果分类。

### 跨边界

进程、服务、队列、数据库、缓存、文件系统和外部 API 的两侧，至少能判断：

- 是否尝试发送。
- 对端是否受理。
- 是否重试或超时。
- 返回结果属于哪一类。

### 状态迁移

记录：

- `previous`。
- `next`。
- 触发原因。
- 产生迁移的实体类型或匿名化标识。

### 静默分支

最容易形成观测盲区的是“不做任何事”的路径：

- 条件不满足。
- 数据未变化。
- 写入为空。
- 已处理或被去重。
- 权限或状态阻止操作。
- 降级策略接管。

这类日志要带稳定的 `reason`，而不是仅写 skipped。

## 4. 判别字段

字段应让几个可能原因呈现不同结果：

| 类型 | 示例问题 |
| --- | --- |
| 存在性 | 目标记录、信号或订阅是否存在？ |
| flag | 命中了哪个分支？是否已取消？ |
| 状态差异 | 前后状态是否发生变化？ |
| 数量差异 | 输入、过滤、写入各有多少？ |
| 相对时间 | 等待发生在哪一阶段？ |
| 来源 | 终态、缓存值或事件由谁产生？ |

避免高基数字段、无限增长数组和完整对象转储。

## 5. 级别与噪声

遵循项目现有级别语义。若没有约定，可采用：

- `debug`：高频路径、逐项细节、正常重试过程。
- `info`：低频关键状态迁移和业务生命周期里程碑。
- `warn`：可恢复但值得关注的异常、降级、数据不一致。
- `error`：操作失败且需要处置，必须带错误分类和必要上下文。

不要为了“方便查”把所有日志提升到 info 或 error。

## 6. 敏感信息

不要记录：

- 密码、token、Cookie、Authorization header、私钥。
- 完整请求或响应正文。
- 用户输入、对话内容、文件内容等未经授权的数据。
- 可直接识别个人身份的信息。

确需关联实体时，优先使用系统已有匿名 ID、受控 hash 或布尔存在性。

## 7. 验证清单

- [ ] 日志通过项目统一 logger 产生。
- [ ] 事件名稳定，变量进入结构化字段。
- [ ] correlation ID 能贯穿相关边界。
- [ ] 成功、失败和静默路径都有必要证据。
- [ ] 字段能区分至少两个可能结果。
- [ ] 没有敏感信息或无界数据。
- [ ] 高频路径使用合适级别或采样。
- [ ] 实际运行已确认事件和字段会产生。
