# 编辑手册：报告到短资讯

## 1. 输入消化

先打开资料再写；PDF 同时关注正文、图表标题、图注和来源。优先用现有 PDF 读取/渲染工具；只有扫描件时再 OCR。标记提取不清的数字，不补猜。

`brief.md` 最少记录：主题、谁读、今天为什么值得看、发布/研究截止日期、用户明确要求、页序、所选设计方式。缺少品牌、字号等可逆偏好不必提问，先用合理默认；无法判断用户指的模型/版本、报告不可读取等关键缺口再询问。

先锁定**这次讲哪件事**：单次发布会、一个产品更新、某篇报告，还是一段时间的动态。把事件日期、资料截止日和不属于本次主题的内容分开；例如“某次 DevDay”不能扩成“当月全部开发者新闻”。用户已有版本时，沿用已确认范围，不靠增加相邻新闻显得更全。

### 事实记录表

每条影响内容的事实至少保存这些信息，可放 `sources.md`：

| 字段 | 要记什么 |
|---|---|
| claim_id | 如 launch-1 / eval-2 / user-3 |
| 内容 | 准备在卡片中怎么说 |
| 类型 | 官方信息 / 平台评测 / 个人测试 / 社区猜测 / 编辑推断 |
| 来源 | 标题、作者、原始 URL；报告中则含页码；视频含时间点 |
| 时间 | 事件发生日期、发表日期、查证日期分别记录 |
| 证据状态 | 已核对原文 / 仅镜像 / 二手转述 / 未核实 |
| 测试范围 | 任务、模型版本、配置、工具、样本数、分母 |
| 可用状态 | 已上线 / Beta / 限量预览 / 即将推出；适用套餐、平台和地区 |
| 用途 | 封面、哪一页、只供背景，或不采用 |

不是每条都要露在图上。图上保留影响理解的短信息，完整细节放来源文件。

用户要求“全部亮点”时，先从本次权威原文列出完整主题清单，再建立“主题 → PNG 页码 → 具体能力/结果 → 必要条件”的覆盖表。验收的是图上的实际正文，标题、来源 ID 或附录中提到产品名不算讲清亮点。一个主题有多项独立新能力时，保留各自的短解释；可合并关联主题、减少例子，不把“全量覆盖”误解为原文逐句搬运。附录承接完整价格口径、名单、方法和来源，但会改变读者判断的 Beta、尚未上线、授权或套餐条件要留在对应图片上。

压缩仍保留公告的核心动作与变化方向：创建、编辑、托管、提高、降低、即将推出等要说清。用已有能力的泛泛描述代替新变化，或把“额度降低”写成“额度调整”，都可能让覆盖表有名字但正文漏重点。

## 2. 核查次序与停止条件

1. 先用用户报告作为选题和线索，不默认报告结论正确。
2. 核对将要发布的核心事实：官方发布公告、原始评测、原作者作品/帖子。变化快的价格、限免、上下线与身份揭晓要查到本次制作日期；用户禁止联网时写“基于报告，资料截至……”，不暗示已查最新。
3. 社区覆盖按**任务类型**找：例如 SQL 调试、前端页面、3D 动画；再补慢、失败、中断这些使用体验。不要收集三个都在说慢的帖子来替代实际效果。
4. 多平台只是渠道覆盖；同一视频被三个媒体转述仍然只有一个案例。同一作者多个任务注明同一人，不伪装成独立多数意见。
5. 原链接读不到可试一次镜像/字幕/可见截图，并如实标识；仍不可核对则省略或明确二手身份。不要连续搜索同一件事几十轮。
6. 单个新模型有可靠上线信息、可用评测和 2–3 个有细节的案例时，可以开始制作；发布会合集则以范围清单及关键事实核对为起点，不强求每项都有社区实测。只为缺失的核心结论继续查，不为“资料多”无限延迟排版。案例不足就减内容或标注缺口，不凑正反各半。

实测细节比空泛好评更有用：“换色、缩放可用，但纽扣形态不清”优于“前端很强”。不能把未验证的帖子数量、点赞数、比例当事实。

## 3. 推荐页面与删减顺序

| 页面作用 | 最少回答 | 适合的视觉 |
|---|---|---|
| 封面 | 是谁？发生了什么？为什么点开？ | 名称大字、新闻标签、一个主题视觉、看点 |
| 介绍 | 时间、平台、产品类型、开发方/使用状态 | 时间节点、产品卡、用途示意 |
| 效果 | 在什么任务中达到什么水平？ | 通过率、得分条形图、前后对比、测试结果矩阵 |
| 社区 | 做成了什么？哪里不足？当时好不好用？ | 2–3 条“任务→结果→作者”，后接早期问题 |
| 收尾 | 已知与猜测的边界/现在怎么用 | 线索对照、结论、访问方式 |

其它题材可调整主线：产品更新用“新功能 → 实际任务怎么变化 → 使用范围”；科研资讯用“新结果 → 实验与对照 → 局限与可用性”。无需为每条资讯增加模型归属页或 benchmark。

介绍中的部署方、接入平台、模型开发方分开写。效果之后再补体验，不把耗时最长的条形图当性能亮点。若读者关心效率，单独清楚标“耗时，越低越好”，并同时解释质量/成本权衡。

内容太长：先删重复解释和无用免责声明，再删次要案例，再合并相关内容；只有页数预算允许才多一页，不先缩正文到看不清。避免三条相似反馈和无证据的“全面领先”。

### 含封面的页数预算

在排版前写清本次最大图片数、是否含封面、每页对应主题和主视觉。封面占一张；备用封面、总览、来源图若也准备发布，均占发布额度。用户说“最多 N 张”是上限，不是必须填满的目标；不能把正文 N 张再额外加封面。该用户认可的发布会案例要求最多 18 张含封面，这是创作约束，不能当作平台永久规格。

合集先按读者任务分组，例如“模型与成本、开发工具、协作与生态”，关联功能可以同页。缩减时先移出完整名单与重复口径，再去掉次要案例；保留每项亮点的能力/变化和关键可用条件。若全量核心信息仍无法在约定上限内清楚表达，说明具体冲突并给出可审阅的取舍，不擅自超张数或隐去亮点。

## 4. benchmark 不出错

- 写清模型版本、任务、日期、Agent/推理设置、样本数、评分定义。
- `pass@4` 是最多四次中成功一次，不能写成单次成功率。
- 28/31≈90.3%，榜单显示90%是取整，不要把两者当冲突。
- 基础配置与加文档配置分别比较，不拿有辅助工具的一侧对无工具另一侧来宣称胜出。
- 不同测试集、不同满分、不同任务不要拼成同一排行。没有可比数值就用文字/矩阵。
- 通过代码检查不等于视觉质量满分；编译通过与最终作品分别记录。
- 0 起点的普通条形图最稳妥。若特殊场景用非零基线，要显著标明；不要靠截轴放大差距。
- 无数据不用雷达图、星级或自行编造总分。数据稀少时做事实卡更好。

## 5. 文案风格与问句钩子

不写：“这不仅是一次发布，更是……”“不是……而是……”“颠覆/炸裂/吊打”或机械三连排比。

可用：“9 月 25 日上线，开发方未公开。” “31 项通过 28 项。” “作者称交互可用，材质表现欠佳。”

封面问“超过 X？”时，必须具备相关比较证据，并在效果页和发布文案中回答。若数据是持平，就写持平并限定测试；若无比较依据，换成“表现如何？”或一个已证实看点。问号本身不提供保守性。

发布文案默认给一份推荐稿：一个简短标题、1–3 个短段的正文、3–5 个相关话题标签。正文通常约 80–160 汉字，按用户要求和信息量调整；说明这次有什么新消息、最值得看的亮点或读者能从图集中获得什么，不必逐页复述。按题材取舍效果与体验，有依据才写社区结果，不强凑固定顺序。

文案必须对应最终图集：亮点、页数、日期和数字均核对最终版本；已开放、预览、即将推出等影响使用决策的条件保留。不要把制作过程、验收结果、下载说明混进发布正文，也不要补入图集和来源未支持的宣传判断。

制作完成时，在最终回复中直接给出这份可复制的完整文案，并同步保存到 `post-copy.md` 和发布包。默认不列多份备选，用户要求多个版本时再提供。若用户只要求给已完成图文补发布文案，直接根据成品提供，无需重新调研或制作图片。只在影响使用决策时保留训练数据、使用限制等提示。

## 6. 身份与不确定性

名称联想、推理风格、token 计数只能按其证据强度写。分词规则相似不证明权重相同或公司相同。不要给来源未提供的身份概率。“目前未公开”应有截止日期；若已经揭晓，应改写主线，不继续造悬念。

不为了严谨塞满“不能判断”“样本有限”大框。在涉及个案的页脚标明个人测试、来源和未复现，正文直接归因给作者。用户删过某块说明，后续版本不悄悄恢复。
